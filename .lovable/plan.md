## 3. Can an external Supabase be connected later from this code?

Technically the code is portable: every backend call goes through `createClient` driven purely by the env variables above, so pointing the app at another Supabase project is a matter of changing those values and replaying the 191 migrations. There is no code-level lock-in.

However, on the Lovable platform side:
- Once Lovable Cloud is enabled on a project it cannot be disconnected or swapped for an external Supabase inside this project. The `.env` and the `src/integrations/supabase/*` files are regenerated by the platform, so hand-edits would be overwritten.
- The practical paths are:
  1. Resume Cloud (add credits). Fastest, zero data risk; everything comes back as it was.
  2. Remix into a new project without Cloud, connect your own Supabase there, apply `supabase/migrations/*` in order, re-add all secrets, re-register webhook URLs (Stripe, Tabby, Tamara, OTO), and migrate data. Data export requires the current backend to be running first, so option 1 is a prerequisite for a full migration anyway.

What cannot be recovered from the repo alone: row data (orders, customers, products), storage files (product images), auth users/passwords, and the server secrets.
